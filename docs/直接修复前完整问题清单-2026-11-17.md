# DataMind 直接修复前完整问题清单

日期：2026-11-17。范围：ETL、MySQL 当前汇总数据、FastAPI 指标与问数接口、Agent 全链路、图表配置、脱敏、测试及交付说明。

本清单是后续直接修复的统一范围。当前发现的问题合并为 **12 类**，不能把同一根因的多个案例当成多轮新增需求。业务代码与数据库尚未修改，未重跑 overwrite ETL，未调整密码和授权。

“完整”指本轮排查范围内已发现问题的集中清单，不代表穷尽所有输入组合。本轮新增 26 项隔离诊断、2 项针对性补证、4 次真实 HTTP 查询、3 次只读 SQL 对照。隔离诊断使用合成输入或模型文本，不能表述为线上自然发生的故障；其中最初 C04 含排行词未触发饼图，结论以补证 C04b 为准。

## 一、真实接口已经复现的错误

| 用户问题 | 实际结果 | 应有行为 |
|---|---|---|
| 按 GMV 占比降序列前三品类，只返回名称和占比 | 正确查询 9.14%、8.25%、7.88%，程序追加“R$25.27” | 百分比不能标为金额；遵守用户要求的返回范围 |
| 2017 年最后一个月的订单数 | 正确查出 2017-12、5,620 单，却称是数据集末月且仅有三天 | 保留 2017 年限定，不能套用 2018-09 的截止说明 |
| 2018-08-01 当天的去重下单用户数 | HTTP 422，称无法精确回答 | 现有日汇总可直接回答：307 人 |
| 2017 年每日去重下单用户数趋势 | HTTP 422，称无法精确回答 | 可按日期筛选日汇总，保留逐日粒度；数据库存在该年度 361 条日记录 |

前两项真实调用证据在 `回答事实真实边界补测-2026-11-17.json`，后两项及独立 SQL 对照在 `直接修复前集中排查补证-2026-11-17.json`。未把缺记录日期自动解释为零人；是否补零需有明确业务约定。

## 二、统一修复清单

### DM-01／P1：指标识别依赖字段名子串，金额、占比、均值、计数混淆

位置：`agent/nodes/response.py:57`、`:134`、`:224`、`:237`。

- `gmv_ratio` 被视为金额相加并标 R$，已真实复现。
- `avg_order_value` 被识别成订单数，隔离诊断中被转成整数后相加；最新月模板也将其标成“单”。
- `order_date` 排在 `order_count` 前面时，识别到日期列，导致订单合计丢失；同一结果仅换列顺序就改变“核验事实”。
- 问每月订单数时，图表可选中排在前面的 `avg_order_value`；金额使用中文别名“销售额”时单位变成 count。

修复方向：对支持的指标明确语义、单位和可加性；兼顾安全的 SQL 输出别名来源。无法识别时保守返回表格或原值，不能猜测货币/计数或强行生成合计。

验收：百分比、平均值、日期、排名不再被当金额/订单累加；交换字段顺序不改变语义；订单问题图表选订单字段，别名不导致错误单位。

证据：R02、R03、R04、R11、C01、C05。

### DM-02／P1：订单去重口径与实际聚合粒度不匹配

位置：`agent/nodes/response.py:90`、`:180`。

- 任意排行榜的行订单数相加，都追加“各卖家……跨卖家重复”的说明；品类排行、月份排行也受到影响。
- 隔离输入的各月订单 2、3 被解释为卖家关联订单，丢失月份互斥的事实。
- 品类前 3 名的结果也被叫作“各卖家”，并被强制追加用户没有要求的合计。

修复方向：区分全局、月份、品类、卖家粒度；只做语义上成立的汇总，标签必须与结果维度相符。跨品类/卖家关联订单不能冒充全局去重订单；跨月订单也不能无条件被说成跨卖家重复。

验收：同一套用例覆盖月份、品类、卖家和全局订单，口径说明准确且不添加无关汇总。

证据：R07、T02。

### DM-03／P1：历史月份、全局末月与月份完整性混为一谈

位置：`agent/nodes/response.py:18`、`:46`、`:134`；`agent/nodes/sql_generation.py:25`；`backend/data_dictionary.py` 的覆盖范围描述。

- 历史年度最后一月被误称为整个数据集末月，已真实复现。
- 对任意结果月直接引用固定截止日的“日”，称该月仅覆盖三天。
- 即使行内截止日期是 2024-02-29，也会断言该月不完整。
- 覆盖日期分散硬编码在回答、SQL 提示和字典里，当前与数据一致，但更新数据时存在不同步风险。

修复方向：以真实覆盖元数据核对目标月份，保留用户时间范围；采用真实日历判断月末，仅在有依据时说明部分月份，缺少依据时不得断言完整或不完整。集中管理必要的覆盖信息，避免多处独立常量。

验收：2017-12、全局末月 2018-09、完整月末及闰月都正确；历史月份不再套用全局末月天数。

证据：R09、R10、此前真实边界 HTTP。

### DM-04／P1：回答后校验只追加修正，保留原有错误与相反结论

位置：`agent/nodes/response.py:180`、`:325`。

- 注入精确但错误的 Top20 合计 3,344,000.00／20,000，原文保留，再追加正确 3,292,633.06／18,908，形成同答矛盾。
- 仅针对部分模糊词和固定短语做正则替换；“2018-09 为完整月份，经营大幅下滑”可原样保留，再追加截止说明。
- “本月完整，经营崩溃”等改写能绕过检查，可能将覆盖不足解释为经营恶化。
- 提示词要求与强制事实说明存在冲突，不能依赖多次追加说明解决。

修复方向：控制最终回答中的关键事实来源与范围，替换或重建冲突段落；无法验证的经营归因不输出。不要用不断扩充特定句式正则作为最终保证。

验收：错误模型文本、同义改写、正确但含不完整末月的趋势，最终回答都不自相矛盾；金额、订单及数据覆盖结论可回溯到查询结果。

证据：R01、R12、R13。均为隔离故障注入，不是声称这些模型文本已在线上自然出现。

### DM-05／P1：查询范围、返回子集和截断范围没有贯穿回答

位置：`agent/nodes/response.py:57`、`:180`、`:301`、`:351`；`agent/state.py` 与执行结果元信息的传递处。

- 结果按 TopN 或执行层行数上限返回时，追加“本结果集合计”仍不足以消除原文“全部卖家已列出”等全量表述。
- 同一回答可前文称全量、末尾称只返回前 1000 行。
- 汇总逻辑缺少可靠的指标来源和查询范围信息，用户未要求合计时也会被强制追加。

修复方向：从实际查询/执行结果保留必要范围信息；截断或 TopN 结果只描述对应子集，完整性不明时不得称全量。最终文本与图表共享范围，不用末尾备注掩盖前文错误。

验收：完整结果、TopN、截断结果分别测试；不得把子集合计写成全局值，不得同时出现全量与截断的矛盾声明。

证据：R08、T02。R08 为合成截断状态，不代表真实查询本轮触及 1000 行上限。

### DM-06／P1：能力判断过宽，拒绝可由现有表准确回答的问题

位置：`agent/nodes/sql_generation.py:36`。

当前检测到“去重用户”与年份/日期就判定不能回答，没有区分单日、逐日序列、期间去重总数。

修复方向：单日及保留逐日粒度的查询允许读取 `dws_daily_active_users`；跨日精确去重总数仍应拒绝，不能累加每日人数冒充。

验收：2018-08-01 返回 307；2017 年每日趋势成功且逐行与数据库一致；2017 年整体去重客户数仍返回准确的 unsupported。

证据：G01、G02、LIVE_D01、LIVE_D02、只读数据库对照。

### DM-07／P2：图表维度和百分比分母缺乏验证

位置：`agent/nodes/response.py:260`。

- 把第一个非数值字段当 X 轴；品类在日期之前时，多品类日趋势以品类为轴且没有系列分组。
- 没有维度时也可能生成 X、Y 都为金额的折线图。
- 仅因 ratio 合计约 100 就声明“全局 GMV、完整覆盖”；合成子集占比 60/40 也被这样标注。

修复方向：优先识别真实时间/分类维度，多个维度需要明确系列或返回表格；没有合理维度时不画趋势。饼图必须有分母与覆盖依据，不能只凭合计 100 猜测。

验收：列顺序变化、多分类时间序列、无维度、子集占比与真正全局占比分别覆盖。

证据：C02、C03、C04b；C04 原问题带“前三个”，实际走柱图，不作为饼图错误证据。

### DM-08／P2：空值和不规范数值的处理会伪造零或抛异常

位置：`agent/nodes/response.py:57`、`:219`、`:283`。

- `total_gmv = NULL` 在事实计算中变成已核验的 0；未知与零没有区分。
- 金额字符串含货币符号/千分位时，事实计算抛 Decimal.InvalidOperation，节点无法正常返回。
- 数字/非有限值等边界缺少统一可信校验；本轮未将所有非有限值分支逐项复现，应在修复回归中覆盖。

修复方向：保留 NULL 语义，检查实际可用数值；不能解析的指标不生成已核验合计，给出受控处理，避免异常扩散或静默转零。

验收：NULL、零、合法 Decimal、格式化字符串、非有限值及混合空值均有明确行为；平均数不再被 int 截断。

证据：R03、R06、T01。R05 的模型文本未必包含零，明确的错误证据是 T01 的内部事实结果。

### DM-09／P2：UNSUPPORTED 识别发生在响应格式规范化之前

位置：`agent/nodes/sql_generation.py:85`、`:98`。

模型返回标准 sql 围栏包裹的 `UNSUPPORTED:` 时，被当作 SQL 输出且错误类型为空，可能误入 SQL 校验/重试。text 围栏变体也不被正确处理。

修复方向：先规范化外围格式，再识别 unsupported 与 SQL；保留现有 SQL 正文保护，不宽松放过不合法 SQL。

验收：普通文本、前后空白、sql/mysql 围栏及明确的非 SQL unsupported 响应走一致的 422 能力错误，不进行数据库执行。

证据：G03、G03b。

### DM-10／P2：Schema 响应结构校验不完整

位置：`agent/nodes/schema_retrieval.py:60`、`:74`、`:83`。

`_valid_table` 接受缺少 table_desc 的表、缺少 desc 的字段，格式化时抛 KeyError，绕开已有的 Schema 服务故障分类。

修复方向：完整校验格式化必需的嵌套字段和类型，明确处理可选字段，损坏响应按服务失败/部分失败规则处理。

验收：缺表描述、缺字段描述、非字典字段、空结果、部分失败及全失败均受控，不出现 KeyError。

证据：S01、S02。为模拟上游畸形响应，未声称当前本地 Schema 接口正在返回损坏数据。

### DM-11／P2：递归脱敏遗漏字典键

位置：`agent/redaction.py:34`；调用方 `backend/api/chat.py`、`backend/main.py`。

递归处理值，但字典键仅 str 转换；当键中含配置秘密时原样保留。已用临时合成秘密复现，不涉及披露真实凭据，未发现真实泄露事件。

修复方向：字符串键也经过脱敏，并考虑替换后的键冲突，避免静默覆盖响应数据；保持嵌套值及短秘密的现有保护。

验收：键、值、数组、嵌套对象、异常正文均不出现配置秘密；覆盖脱敏后键冲突的受控行为。

证据：SEC01。

### DM-12／P3：测试与交付说明未覆盖上述语义，运行环境说明不一致

## 四、直接修复顺序和完成标准

1. 先修共享语义根因：DM-01、02、03、05、08；覆盖 response、SQL/执行元信息、state、数据字典与相关调用方。采用足够解决当前问题的最少元信息，不建立超出项目需要的通用语义平台。
2. 统一最终回答与图表：DM-04、07；金额、单位、粒度、时间范围和完整性使用同一依据，避免继续在错误回答末尾拼补丁。
3. 修协议与边界：DM-06、09、10、11；用隔离测试阻止错误 SQL 执行和真实秘密暴露。
4. 完成 DM-12：运行相关回归和真实问数，按当前数据做只读对照，记录真实测试数、限制和源码版本。

完成必须同时满足：本清单中的可复现故障消失；有效保护不退化；核心数据指标不变；准确拒绝现有数据无法回答的问题；最终回答、SQL、结果行和图表互相一致。

未进行：overwrite ETL 重跑、生产部署、压力/长稳测试、修改数据/账户权限。当前没有这些行为的必要性；测试覆盖以本机已发现问题和现有接口为界。
