## 待修复问题

### 1. [P1] 只读校验可绕过，且 Agent 使用有写入和 FILE 权限的账号

位置：`agent/nodes/sql_execution.py:29`、`:47`、`:133`；`agent/config.py:13`。

`_validate_sql` 只检查字符串包含关系。`SELECT 1 INTO\nOUTFILE 'D:/DataMind/datamind_acceptance_do_not_execute.txt'` 用换行分隔 INTO 和 OUTFILE 后通过校验；`SELECT User,Host FROM `mysql`.`user`` 用反引号限定系统库后也通过。经过 `_enforce_limit` 之后，两条 SQL 均被实际 MySQL PREPARE 接受。没有执行它们。

实查当前 Agent 账号拥有 FILE、INSERT、UPDATE、DELETE、CREATE、DROP 权限，默认事务非只读。不能把“SELECT 开头 + 关键词黑名单”视为已落实只读边界，系统库及 Schema 外表也没有执行层白名单限制。

修复要求：查询账号仅授予所需 ADS/DWS 表的 SELECT 权限；按 SQL 结构校验单条只读查询，禁止 INTO 文件、系统库和非授权表。保留 ETL 所需写权限时，应使用独立 ETL 账号。增加上述绕过输入的回归测试。不要实际执行写文件探针。

### 2. [P2] 行数硬上限未覆盖合法 LIMIT 写法，fetchall 先加载全部结果

位置：`agent/nodes/sql_execution.py:65`、`:145`。

复现：`_enforce_limit('SELECT 1 LIMIT 0, 999999')` 原样返回，未限制 row_count；`SELECT * FROM (SELECT 1 LIMIT 1) t` 中的子查询 LIMIT 被当作外层 LIMIT，外层不再追加限制。字符串中的 `limit 1` 也会被误识别。

`cursor.fetchall()` 在 `rows[:MAX_ROWS]` 之前调用，因此末尾切片只限制返回给调用方的列表，不能防止数据库执行和客户端加载大结果集。

修复要求：按外层查询结构限制结果数，正确处理 LIMIT offset,count、LIMIT count OFFSET offset 和子查询；使用有界提取，必要时配合流式游标及查询超时。增加对应回归测试。

### 3. [P2] 趋势总结只读取前 20 行，遗漏最新五个月

位置：`agent/nodes/response.py:75`、`:78`。

真实趋势返回 2016-09 至 2018-09 共 25 行，但 `_summarize` 固定截取 `rows[:20]`，模型实际只能看到截至 2018-04 的数据。通过捕获模型调用参数确认，2018-09 不在总结输入中。实际回答主要总结早期上涨，未覆盖最后五个月，却以整体趋势的口吻回答。

修复要求：对这类有限月度序列传入完整数据，或提供涵盖首尾、极值和最新阶段的完整统计摘要；更大结果集如需抽样，须明确范围，避免以部分数据推断整体。当前数据币种为 BRL，实际趋势回答使用“元”，也应统一业务口径。

### 4. [P2] 数据库或 SQL 执行失败仍返回业务 success

位置：`backend/api/chat.py:56`、`:57`；`agent/nodes/response.py:104`。

连接失败及 SQL 重试耗尽会被图转换成普通文字答案，`chat()` 随后仍构造默认 `code=200, message=success` 的响应。直接模拟图返回连接故障后调用真实 chat 路由函数，复现了 `code=200`、`message=success`、`answer=数据库连接失败`。

虽然文字答案已能区分故障与空结果，但调用方无法可靠地通过状态区分查询成功和失败。

修复要求：将图中的错误类别传递到 API，提供明确的失败 code/状态，成功空结果保留成功状态。增加路由级连接失败、SQL 失败和成功空结果的测试。
