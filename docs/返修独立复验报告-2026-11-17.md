## 仍需修复

### 1. [P2] SQL 提取会破坏末尾带反引号的正常标识符

位置：`agent/nodes/sql_generation.py:61`、`:62`。

复现输入（合法且不要求结尾分号）：

```sql
SELECT total_gmv FROM `datamind_ads`.`ads_gmv_overview`
```

`_extract_sql` 中的 `text.strip().strip("`").strip()` 去除了真实表名末尾的反引号，得到：

```text
SELECT total_gmv FROM `datamind_ads`.`ads_gmv_overview
```

独立验证：固定 SQL 生成节点的模型响应为上述合法输入，经过真实 `sql_generation_node` 后交给 `sql_execution_node`，得到 guard 错误“SQL 无法解析”。并非仅对辅助函数的推测。

影响：SQL 提示词没有要求结尾分号，模型返回这种常见合法写法时会无谓重试；如果重复返回同样格式，会最终失败。

修复要求：只剥离外围 markdown 代码围栏，完整保留 SQL 内容中的标识符引号与字符串。不要用 strip("`") 处理 SQL 正文。增加“无分号、最后一个字符是合法反引号”的完整生成到执行回归测试，同时覆盖有围栏、无围栏和带分号输入。

### 2. [P2] AST 校验仍存在 CTE 作用域及嵌套加锁检查遗漏

位置：`agent/sql_guard.py:112`、`:141`、`:149`。

#### CTE 名称绕过显式库名检查

```sql
WITH ods_customers AS (SELECT 1 AS x)
SELECT * FROM datamind_ods.ods_customers
```

`resolve_tables` 将所有 CTE 名称放入全局集合，然后对同名的所有 Table 节点直接 continue。即使引用显式指定了 datamind_ods，也因名称与 CTE 相同而跳过白名单校验。

实际 `prepare_readonly_query` 允许该输入，返回 tables=[]，并渲染出真实非授权表引用。用连接前抛出异常的 mock 包住 `pymysql.connect` 后运行真实执行节点，确认已经到达连接步骤，未以 guard 类错误拒绝。

#### 子查询中的加锁读未检查

```sql
SELECT * FROM (
    SELECT total_gmv FROM ads_gmv_overview FOR UPDATE
) t
```

`check_structure` 只检查根节点 `stmt.args.get("locks")`，没有遍历子查询的锁节点。该输入也通过 prepare_readonly_query，渲染结果保留 FOR UPDATE，并能到达连接步骤。未实际执行加锁查询。

影响与边界：只读账号的权限已落实，数据库仍能阻止非授权表读取，本轮没有发现可借此读取 ODS 数据的权限突破。但“执行层一律拒绝非授权表和加锁读”的声明尚不成立，拒绝类别、审计元信息和行为也会不符合预期。

修复要求：按 SQL 作用域识别真实 CTE 引用，显式带库名的引用始终视为物理表并校验授权；不得因为同名 CTE 跳过检查。遍历整棵语法树的锁节点，拒绝任何层级的 FOR UPDATE / LOCK IN SHARE MODE。增加执行节点回归测试，断言策略拒绝且连接函数从未被调用。
