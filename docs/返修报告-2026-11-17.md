## 一、SQL 只读边界（[P1] 已关闭）

### 原问题
1. `_validate_sql` 用字符串包含匹配，`SELECT 1 INTO\nOUTFILE '...'` 换行即可绕过；
2. 反引号限定 `` `mysql`.`user` `` 可绕过系统库限制；
3. Schema 外的表没有执行层白名单；
4. Agent 使用 root 账号，具备 FILE 与写权限。

### 修改文件与原因
| 文件 | 原因与改动 |
|---|---|
| `agent/sql_guard.py`（新增） | 用 **sqlglot（MySQL 方言）** 把 SQL 解析成语法树后做结构判断，取代字符串黑名单：① 恰好一条语句，解析失败一律拒绝（fail closed）；② 顶层必须是 SELECT/UNION/INTERSECT/EXCEPT；③ 语法树里出现 `Into` 节点（含换行写法与 `INTO @var`）即拒绝；④ 任何表引用的库不在 `datamind_ads/datamind_dws` 或表不在白名单即拒绝（覆盖反引号限定系统库、ODS 库、不存在的表）；⑤ 拒绝 `FOR UPDATE`/`LOCK IN SHARE MODE`、`@@系统变量`、`load_file/sleep/benchmark/get_lock` 等函数 |
| `agent/nodes/sql_execution.py` | 改为调用 `prepare_readonly_query()`；连接改用只读账号；连接后 `SET SESSION TRANSACTION READ ONLY` + `SET SESSION MAX_EXECUTION_TIME=15000` 双保险；错误分类新增 `guard`（安全拒绝） |
| `agent/config.py` | 数据库连接改为 `MYSQL_QUERY_USER` / `MYSQL_QUERY_PASSWORD`（环境变量 / `agent/.env`），不再出现 root 与明文密码 |
| `backend/db/connection.py` | 指标接口也改用同一只读账号（读多写零），凭据同样来自 `agent/.env` |
| `agent/requirements.txt` | 新增 `sqlglot`、`python-dotenv`、`cryptography` |

  `GRANT USAGE ON *.*` + 7 条 `GRANT SELECT ON datamind_ads.ads_gmv_overview / ads_gmv_trend /

## 二、行数上限与 SQL 文本处理（[P2] 已关闭）

### 原问题
`LIMIT 0, 999999` 未被限制；子查询 LIMIT 被误当成外层；字符串里的 "limit 1" 干扰判断；
`fetchall()` 先全量加载再切片；表名补全误改字符串字面量；`_extract_sql` 按分号切分导致
`SELECT 'a;b' AS note;` 被截断。

### 修改与证据
| 修改 | 证据 |
|---|---|
| 限行改为只作用于最外层 AST 节点，逐值比较并改写（保留 OFFSET） | `LIMIT 0, 999999` → `LIMIT 1000 OFFSET 0`（capped）；`LIMIT 999999 OFFSET 20` → `LIMIT 1000 OFFSET 20`；`LIMIT 50 OFFSET 500` → kept |
| 子查询不被误判 | `SELECT * FROM (SELECT 1 LIMIT 1) t` → 内层 `LIMIT 1` 原样 + 外层 `LIMIT 1000`（两份 LIMIT 并存） |
| 字符串不干扰 | `SELECT 'limit 1' AS s` → 仍追加外层 `LIMIT 1000` |
| 非字面量 LIMIT 拒绝 | `LIMIT 1+1` → `LIMIT 必须是整数字面量`；`LIMIT @@max_allowed_packet` → 系统变量拒绝 |
| 有界提取（不靠 fetchall） | 连接使用流式游标 `SSDictCursor`，`fetchmany(MAX_ROWS+1)` 后截断；实测 `dws_daily_trade`（18,927 行）→ 返回 **1000 行**、`result_truncated=True`；`ads_gmv_trend`（25 行）→ 25 行、`truncated=False` |
| 表名补全不改字面量 | `SELECT 'ads_gmv_overview' AS label FROM ads_gmv_overview` → 字面量保持原样，仅真实表被限定为 `` `datamind_ads`.`ads_gmv_overview` `` |
| SQL 提取保留字符串内分号 | `_extract_sql` 不再按 `;` 切分，只剥 markdown 标记；`SELECT 'a;b' AS note;` 正常执行；`SELECT 1; SELECT 2` 在执行层明确拒绝 |

## 四、失败仍返回 success（[P2] 已关闭）

### 修改
| 文件 | 改动 |
|---|---|
| `agent/state.py` | 新增 `error_category`（connection / guard / sql / None）、`result_truncated`、`sql_meta` |
| `agent/nodes/response.py` | 各失败分支写入 `error_category`；成功空结果保持 None |
| `backend/api/chat.py` | 按 `error_category` 返回真实状态码：连接失败 **503/503**、安全拒绝 **400/400**、SQL 失败 **500/500**、成功（含空结果）**200/200**；错误提示对前端不含内部细节；响应统一做凭据脱敏（把密码/密钥替换为 `***`） |

### 证据
| 场景 | 结果 |
|---|---|
| 路由级注入连接失败 | HTTP **503**，`code=503`，`message=数据库暂时不可用，请稍后重试`，`error_category=connection` |
| 真实链路连接失败（另起实例指向 3399 空端口，未停生产 MySQL） | HTTP **503**，8.9s 返回，未空转重试 |
| 路由级注入 SQL 失败（重试耗尽） | HTTP **500**，`code=500` |
| 路由级注入安全拒绝 | HTTP **400**，`code=400` |
| 成功空结果（真实：问 2019 年 GMV） | HTTP **200**，`code=200`，`message=success`，`row_count=0` |
| 响应含密码文本时 | 响应体中密码被替换为 `***`，未泄露 |

重试逻辑（图级注入，未调模型、未停库）：
SQL 持续失败 → 执行节点共调用 **3 次**（1 次 + 重试 2 次）后返回 `error_category=sql`；
一次失败后成功 → 调用 **2 次**并返回结果；
连接失败 → 调用 **1 次**，直接返回 `error_category=connection`（不重试）。

## 七、未验证项与说明

1. **ETL 未重跑**：数据完整（22 张表行数、四方 GMV 一致），按任务要求不做 overwrite；
   因此本轮未验证"从空库一键重建"。
2. **未执行写/文件探针**：按任务要求不做；写与 FILE 权限缺失由 `SHOW GRANTS` 白名单证明，
   库层非授权访问阻断由 1142 实测证明。
3. **会话只读的兼容性**：`SET SESSION TRANSACTION READ ONLY` 在不支持的老版本 MySQL 上会被
   静默跳过（不影响查询，权限层仍是唯一防线）；当前 MySQL 8.4.11 已生效。
4. **大结果集抽样的展示效果**：仅做了提示词与用户提示的单元验证，以及 1000 行截断的执行层验证；
   前端渲染（截断提示/图表轴单位）留待前端联调验证。
5. **状态码变更的兼容性**：`/api/chat` 失败时改为非 200，前端尚未开发，无历史兼容负担；
   若后续有调用方按"永远 200"解析，需同步调整。
6. **前端未开发**（不在本轮范围）。
