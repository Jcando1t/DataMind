## A. SQL 提取破坏合法标识符

位置：`agent/nodes/sql_generation.py`。

`_extract_sql` 对正文执行 strip("`")，会把无分号 SQL 最后一个合法标识符的反引号删除。合法输入 `SELECT total_gmv FROM `datamind_ads`.`ads_gmv_overview`` 经生成到执行链路会变成 guard 解析错误。

修复：仅识别并去除最外围 markdown 围栏，完整保留 SQL 正文的引号、字符串和分号。增加有/无围栏、有/无分号、末尾反引号、字符串内分号及反引号的回归测试。真正多语句仍交给结构校验明确拒绝。

## B. SQL AST 的作用域和嵌套校验遗漏

位置：`agent/sql_guard.py`。

已确认两个输入通过校验，并在执行节点到达连接步骤：

```sql
WITH ods_customers AS (SELECT 1 AS x)
SELECT * FROM datamind_ods.ods_customers;

SELECT * FROM (
    SELECT total_gmv FROM ads_gmv_overview FOR UPDATE
) t;
```

原因：使用全局 CTE 名集合跳过同名表；加锁只检查根节点。

修复：按作用域解析真正的 CTE 引用，显式库名物理表始终校验白名单；遍历所有层级锁节点。覆盖 CTE 同名遮蔽、嵌套 CTE、子查询、UNION 分支及带库名引用。被拒绝输入必须在建立数据库连接前返回 guard 错误。保持合法 CTE、子查询和跨授权库查询可用。

当前数据库只读权限能够阻止上述非授权 ODS 访问，本轮未发现数据读取权限突破。不要将其误报为 root 权限漏洞，也不要因此省略结构校验修复。

## C. Schema 检索不完整、不稳定及失败分类不准确

位置：`agent/nodes/schema_retrieval.py`、`backend/data_dictionary.py`，必要时调整节点状态和错误类别。

1. 真实 `/api/chat` 问“总用户数是多少？”返回“未找到相关数据”，SQL 为 `SELECT '未找到相关数据' AS message`。关键词 user 只命中 dws_daily_active_users，没有检索到含 total_customers 的 ads_gmv_overview；正确值 94,990 已存在。修复用户/customer/customers 的语义映射及检索排序。
2. 关键词经 set 转 list 后只取前三个，选择随进程哈希种子变化。改为稳定、有优先级的去重和筛选，确保限制数量时不随机丢掉核心业务维度；覆盖多关键词及追问。
3. 单关键词失败目前只记入临时列表，未输出声明中的告警；“一个请求成功但无匹配 + 另一个失败”会被误报为全部接口失败。分别统计成功响应、无匹配、部分失败和全部失败，必要时给出降级提示。告警记录需脱敏。
4. 检查 HTTP 200 中的业务 code 与响应结构，不能把业务失败当作成功空字典。

## D. 指标语义与无能力回答的处理

位置：数据字典、SQL 生成及响应节点。

明确标注并落实以下口径：

- GMV 包含 price + freight_value；总客户数为全局去重下单客户，不是登录用户。
- 全局总客户数读取 ads_gmv_overview.total_customers，正确值 94,990。daily_active_users.active_user_count 的全量日合计实际为 97,277，不能相加当作去重用户数。
- 品类订单数跨品类不可直接相加当作全局订单；全局订单总数为 98,207。按月总体订单使用去重订单口径的月度表。
- 环比数值已经是百分数，不得再次乘 100；金额单位统一 BRL。
- 对现有授权汇总表无法准确计算的指标，例如任意自定义时间段的去重客户数，明确说明能力限制或请求澄清；不要用日活累加冒充，也不要为回答方便扩大到 ODS/DWD 的访问权限。
- 不把 `SELECT '未找到相关数据'` 生成的占位行当作真实业务查询成功；区分不支持的问题、成功空结果和执行故障。保留现有 503/500/400/200 语义，并明确“不支持”的响应约定。
- “最近一期/最后一个月”默认按数据集最大时间定位；真正要求当前日历时间时应按用户要求，并说明数据覆盖范围。

## E. 图表配置可能误导

位置：`agent/nodes/response.py`。

1. 品类前三名返回全局占比 9.14%、8.25%、7.88%，合计只有 25.27%，当前自动选饼图。常见饼图会归一化这三项，造成“占全局 GMV”被错误显示为“占前三名合计”。排行优先柱状图；若提供全局占比饼图，必须提供其余品类或明确改用子集分母，不能混淆。
2. 卖家排行同时将 total_gmv 与 total_orders 放入未声明单位和坐标轴的 y 列表。默认按问句选择单一指标；需要比较不同单位时提供明确轴/单位元信息或改为表格，避免前端照配置画出误导性的同轴图。
3. 保留当前 GMV 趋势仅使用 monthly_gmv、覆盖最新月份和 BRL 口径的修复。数据行可保留全部字段，作图配置不必把所有数字都画进去。

## F. 请求输入校验不足

位置：`backend/api/chat.py`。

实测空白 question 能通过路由并进入模型调用。chat_history 使用任意 Dict[str,str]，缺少角色和大小限制。

修复：question 去除首尾空白后要求非空；为问题长度、历史条数及单条消息长度设合理上限；历史消息使用明确模型，仅允许业务需要的 user/assistant 角色。无效请求在模型或数据库调用前返回 422，避免将历史中的 system/developer 或异常结构直接传给模型。不要通过静默截断改变用户问题的语义。

## G. 异常信息和脱敏不完整

位置：`backend/api/chat.py`、`backend/main.py`、必要的日志位置。

实测注入合成异常文本后，chat 的 500 响应直接回显异常详情；全局异常处理器也直接返回 str(exc)。`_payload` 只对 answer 脱敏，合成配置凭据标记仍能出现在 sql 和 rows 中。

修复：未处理异常对外只返回稳定、简洁的失败信息；详细原因进入脱敏日志。检查完整响应路径，确保当前配置凭据不会通过 SQL 显示、数据、错误正文或日志泄露。保留适当的业务错误说明，不向用户暴露数据库内部异常原文或第三方接口原始错误。测试使用合成标记，不输出真实密码或密钥。

## H. 特殊字符密码导致 SQLAlchemy URL 解析错误

位置：`backend/db/connection.py`。

当前直接拼接用户名和密码生成 URL。使用包含 @、:、#、/ 的合成密码可以复现解析错误，当前纯字母数字凭据可用不等于配置实现正确。

修复：使用 SQLAlchemy URL.create 等结构化方式传入连接参数，或正确转义，不把含密码 URL 输出到日志。增加合成特殊字符密码的解析往返测试，无需更改真实账号密码。

## I. 运行保障需补验证
